# Filed at B2-R1 — found, not fixed

Three items found during B2-R1 (patient-facing cancellation) that were
deliberately **not** built in that session. Each is written so whoever picks it
up starts from the analysis rather than repeating it.

---

## B2-R1-F1 — a reminder already CLAIMED is still sent after the appointment is cancelled

**Severity:** low-frequency, patient-visible. Narrow window, real.

**What happens.** `reminderCron.claimDueAppointments` (`src/scheduler/reminderCron.js:97-98`)
filters `a.reminder_status = 'pending' AND a.status = 'booked'`, so a cancelled
appointment can never be claimed. That half is free and is asserted
(`tests/appointment/cancel.integration.test.js`, *"reminderCron never claims a
cancelled row"*).

The gap is the row that was **already claimed**. Once `claimDueAppointments`
flips it to `'sending'` and returns it, `processDue` iterates the rows **already
fetched into `due`**, and `processReminder` **never re-reads `status`**. A cancel
landing in that window does not and cannot stop the send: the patient receives
*"Reminder: your appointment with Dr. Rao … is on …"* for an appointment they
cancelled seconds earlier. `reminderCron.js:241` then writes
`reminder_status = 'sent'` on the cancelled row — that UPDATE carries no status
filter.

**Why it is not fixable from the cancel side.** The cancel is a single guarded
UPDATE on `appointments`; it has no way to reach into an in-flight tick. The fix
belongs to the send path: re-check `status = 'booked'` under the row lock before
sending, or add `AND status = 'booked'` to the terminal reminder UPDATEs so a
cancelled row cannot be marked sent. Either is a reminderCron change with its own
test, not a cancel change.

**Why the cancel does not touch `reminder_status` at all.** The column's CHECK is
`('pending','sending','sent','failed','needs_template','needs_review')` — there
is no cancelled value, and adding one is a schema change. The only reachable
writes would be `'sent'` or `'failed'`, and both are lies about what happened.
Asserted deliberately: the cancelled row is left at `'pending'`.

**Bounds — it cannot repeat, and this is why it stayed low priority.**
`reapStuck` returns a stalled `'sending'` row to `'pending'` after 10 minutes,
and the **re-claim filters `status = 'booked'` again**, so a cancelled row is
never claimed a second time. It simply sits at `'pending'` forever, inert. The
window is one tick's send loop, and only for an appointment already inside
`reminder_hours_before`. Asserted as it stands in
`tests/appointment/cancel.integration.test.js`, *"a row already CLAIMED (sending)
is still reminded"* — the test records the real behaviour rather than pretending
it is fixed.

## B2-R1-F2 — `portalLifecycle.integration.test.js:794` is intermittent, and it is NOT a timestamp-truncation bug

**Owner:** F1-R1 (`f7e8a97`), one commit before B2-R1. Not B2-R1's.

**Symptom.** `tests/portal/portalLifecycle.integration.test.js:794` — *"the
trigger moves updated_at and leaves created_at alone, on both tables"* — fails at
`:822` with `tenant_entities.updated_at must move on an UPDATE`, actual `false`.
Observed **1 red in 2 full `npm test` runs** at a clean tree (`1e51fbb`). The file
passes **25/25 in isolation**. Three later full runs were green.

**A hypothesis, measured and REJECTED.** The obvious candidate was millisecond
truncation: `set_updated_at()` writes `NOW()` at microsecond precision and
node-postgres truncates a `timestamptz` into a millisecond-resolution JS `Date`,
so an INSERT and an UPDATE inside one millisecond would compare equal under
`+e1.updated_at > +e0.updated_at`.

Measured against the **local Postgres the suite actually uses**
(`localhost:5432`, via `TEST_DATABASE_URL` — note that measuring `DATABASE_URL`
instead measures the remote database and answers a different question):

| Measurement | Result |
|---|---|
| `clock_timestamp()` distinct values from 200 000 calls | **200 000** |
| clock gap, min / median | **1 µs / 3 µs** |
| INSERT→UPDATE pair, same-millisecond collisions | **0 in 60** |
| INSERT→UPDATE delta, min / median / max | **2 ms / 3 ms / 139 ms** |

At idle the pair is never closer than 2 ms, and under a full 156-suite run
latency rises rather than falls, so collisions get *less* likely, not more.
**Truncation is not the mechanism.** The mechanism is unknown.

**What this saves the next person.** Do not re-derive the truncation theory, and
do not "fix" it by widening the comparison to `>=` — that would make the test
pass without explaining anything and would stop it detecting a genuinely absent
trigger. Ruled out so far: the trigger is unconditionally present in
`schema.sql:319-320` and these suites bootstrap via genesis, so a missing trigger
is not it; and migration `026` being absent from the shared `saas_crm_test`
database is a different problem (below) that this suite does not touch, since it
mints its own scratch DB.

Sibling of the recorded `tests/traces/traces.integration.test.js:247`
intermittent. Neither has an established frequency.

## B2-R1-F3 — the shared test database was one migration behind (FIXED in passing)

`saas_crm_test` (the `TEST_DATABASE_URL` target) was missing migration `026`:
`tenant_entities.updated_at` did not exist there (`42703`). Nothing was failing
because every suite that reads that column mints a genesis scratch DB from
`schema.sql`, but it is the same trap `025` sprang during B2.

Cleared before B2-R1's baseline by running the migration against that database
explicitly. **This is the third occurrence of the same class**: a schema change
lands, the dev database gets migrated, and the shared test database does not. The
durable fix is for the test bootstrap to fail loudly when
`TEST_DATABASE_URL` has pending migrations, rather than for each session to
remember. Not built here.
